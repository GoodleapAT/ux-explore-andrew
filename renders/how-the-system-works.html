How the system works, and why it is built the way it is

This is not about design. It is about how the thinking is kept so that a conversation on any AI surface starts warm rather than cold, and so that corrections compound instead of evaporating when a session ends.

Three mechanisms do that work. A loop, which turns a correction into a rule while the correction is still cheap to write. A map, which says which surfaces can read the memory, which carry a copy of it, and which of those copies go stale. A stack, which says what wins when two things disagree. The rest of the system is consequence.

A

The loop

Why the next session starts warm

A session is a lap of this. The first box and the last two are the load bearing ones. Everything between them is ordinary work.

Complete on structure, not exhaustive on contents. The trigger box lists five of seven triggers. The write-back branch exists because some surfaces can read the memory and cannot write to it, which is the map in the next section.

Why box 1 is a whole box

The changelog is the only file that answers whether anything has moved since you last looked. It is append only, newest at the bottom.

Saying its newest date out loud is a one-sentence staleness check, and it happens before any work, so a surface reading a stale copy reveals itself in its first sentence rather than in its output.

Why the prompt comes at the trigger

A correction is cheapest to write in the moment it is made, while the reason for it is still in the conversation. Saved to the end of a session it arrives as a summary, and a summary of a correction is not a rule.

Writing the changelog row is not the same as telling him. Both happen.

Why two questions and not one

What did we learn about the problem, and what did we learn about how to work on it. The second is the one that gets skipped.

A session where he corrected something and no standard changed is a session that lost work, because the same correction will now be made a third time.

What the loop does not have

No enforcement. Every rule in the system is held by a surface choosing to read it and choosing to comply. Nothing checks.

That is the honest weakness, and it is why the rules are short, why the index fits on one screen, and why the marker on each rule matters more than its wording.

B

The map

No surface can notify another

There is one repository and several surfaces. Two lanes. Above the band, surfaces that read the memory themselves. Inside the band, everything that only has a copy, which means a person has to carry the change. Claude Design sits in both lanes, and that is the interesting one.

Complete on structure, not exhaustive on contents. The two purple lines are the awkward pair: Claude Design reads the memory directly but its own instructions are a stored copy, so its facts stay current while its rules go stale, and only a person can close that gap.

Why a person is in the middle

Not by design. No surface can notify another, so propagation is manual and single threaded through one person.

The system's answer is to make the cost visible rather than to pretend it is not there: every changelog row ends with a column naming which surfaces are now stale and what to do about each.

The read-only problem, and the fix

A surface that can read but not write would otherwise lose everything it learned. The fix is a write-back block: the file, the section, the exact text, and whether it is an append or an edit.

It is written to be pasted, not read. A surface that summarises what should change instead of writing what should be written has not done the job.

Why renders are held at arm's length

Anything in the renders folder is a copy generated from the standards, made for a surface that cannot read the repository. When a standard changes, the render is wrong.

This page is one of those copies. That is why it opens with a banner saying so and naming what it was generated from.

The failure this map did not predict

It covers a rule going stale. It does not cover a fact going stale because the story underneath it moved.

That happened today. The canonical mock data describes a three-trade story that was rewritten into a two-trade one, so the file is now a trap for the next surface that reads it in good faith, and no rule in the system covered it.

The stack

What wins when two things disagree

Highest first. Read it as a tie-break, not as a chain of command. Most of the time nothing collides and the stack never comes up; it exists for the moment something does, so the resolution is not invented on the spot.

Rules are never changed silently

A standard that turns out to be wrong gets replaced, and the replacement records what it replaced and why. A decision that is reversed becomes a new row in the log, never an edit to the old one.

Same reason a change order keeps the original contract value on it.

Some files are append only

The changelog, the idea inbox and both decision logs. Never edited, never reordered, never tidied.

The cost is that they get long and contain things that are no longer true. That is the point: a reversal is only legible if the thing it reversed is still there.

Why the stack ends where it does

Putting what a previous mock did last, below a leaning, is deliberate. It is the most available reason in the room and the weakest one, because a mock is a proposal that survived rather than a decision that was made.

And why nothing external is on it

The team's boards and scripts are read constantly and are recorded as reference, never as input. The rules covering that are all Always, because the failure mode is silent: a position drifts in unattributed and then gets defended as ours.

Four things carry almost all of it. None of them is about having read the whole repository, which nobody has.

What to doWhy, in one line

The one rule most likely to trip you

Ask before building or rebuilding anything. Every time, even when the previous message asked for it, even when it is a small revision.

What the system is deliberately not

Not any team's record, and not authoritative for anyone but Andrew. Contributions to a team repository go as a branch and a pull request.

And not a backlog. Ideas carry an appetite and a revive condition precisely so the catalogue does not become one. An idea with no appetite is a note.

Where it is weak, stated rather than hidden

Nothing enforces any of it. Every Always rule is held by a surface choosing to read the standards and choosing to comply. The mitigation is that the rules are short and the index fits on one screen, which is a mitigation and not a fix.

Propagation is one person wide. No surface can tell another that something changed, so every update to a stored copy waits on him noticing and doing it. Two copies are currently overdue.

A render looks authoritative when it is wrong. The banner on this page is the only thing standing between a stale copy and somebody designing from it.

The staleness rules cover rules, not facts. A standard going out of date is handled. A mock data file going out of date because the story underneath it was rewritten is not, and it happened today.
