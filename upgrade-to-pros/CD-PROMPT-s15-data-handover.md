You are receiving **the complete data pack for scenario S15**, a multi-trade project paid in cash. It
is one file, `S15-DATA.md`. **Read all of it before you draw anything.**

## What this file is

**It is the only source of mock data for S15.** Every name, date, price, measurement and money state
that any screen could need is in it. **Do not invent a value that is not in the file.** If something
is missing, say so and it will be added, so that the next screen uses the same one rather than a
second invention.

**Every value carries its provenance**, and the mark matters:

- **SCRIPT** is stated in the scenario's beat script. Treat it as fixed.
- **CANON** is from the project's long-standing worked example. Correct and reusable.
- **OURS** was invented to fill a gap. **You may question any of it**, and section 12 lists all of it
  in one place.

**The file is newer than the Confluence script it derives from.** The calendar was revised today and
the script has not caught up. Section 1 lists every difference. **Where they disagree, the file
wins.**

**One other file is stale and you should not read it for S15:** the project's worked example
describes three trades, a change order and three milestones, none of which are in this scenario.

## The one layout rule, and it is the reason for this round

**The groups usually appear in the same order on every state, and a group that is not needed
collapses in place or disappears from where it was.**

Nothing moves up the page because something above it shrank. A container is the same container at
every point in its life, and what changes is how much of each group is showing, not where the groups
are. **If you find a state where the order genuinely has to change, say so and say why**, because
that is a finding about the container rather than a layout preference.

The previous round broke this rule on every screen and it is why the work was unusable.

## What you are building from

**Twenty one beats are not twenty one designs. They are six containers**, and section 9 of the file
lists them with their states. The project is the one that matters: **seven states of one page**, from
the day after the sale to the day it is paid.

**Build containers, not screens.** A state is a variant of its container, never a new page. **If two
states of one container come out as two different designs, report it** rather than working around it.

**Within a container, build the hardest state first**, then derive the simpler ones by taking things
away. For the project that is beat 19, both jobs complete and the balance due and uninvoiced.
Subtracting is faster and more consistent than adding, and it shows the container's full extent on
the first attempt.

## Three things the file asks you to notice

**Nothing in this scenario is ever blocked**, with one exception. No change order, no failed
inspection, no decline, nothing to chase. **The permits are the only thing anybody waits on**: applied
on 7 August, issued on 11 August. That four-day gap is **the only pending state in the entire
scenario**, so it is the only place any attention treatment is earned.

**There is exactly one amber moment.** For three days, between the jobs completing on 21 August and
the invoice being raised on 24 August, **$72,600 is owed and nothing has asked for it.** Completion is
the trigger, so the money falls due before anybody bills it. The model has no state for this.

**Per-job margin does not exist and must not appear.** Revenue occurs at the project and cost at the
job, and no allocation rule has ever been specified. **Not drawn, not greyed, not labelled
unavailable. Absent.** The file's section 11 lists five more values in the same category.

## Two decisions to bring back rather than make

1. **What the lead is called at 8:07am**, before siding is added at 8:11am. The container is named by
   its contents, so the name changes mid-call. **Nobody has decided what it reads at the start.**
2. **The money card at beat 19 carries the same fact four ways**: a warning badge, a coloured total, a
   status line reading due, and a Create invoice button. **Tell me which of the four you would keep.**

**And one thing that is settled, so you do not re-open it.** The two jobs are **staggered and do not
overlap**: roofing Monday 17 to Tuesday 18, siding Wednesday 19 to Friday 21. Beat 18 is therefore
drawn on **Tuesday 18 August**, roofing complete and siding scheduled to start tomorrow, which is
exactly what its instruction asks for.

## Rules that will bite, beyond the layout rule above

- **No reference codes or record identifiers.** No job numbers, no invoice numbers, no proposal
  numbers. Call the thing by its name: the siding job, the master invoice.
- **No explanatory copy inside a screen.** Anything you want to say goes in your reply.
- **Placeholder what the current question does not touch, and label it as a placeholder.**
- **Colour only where somebody has to act, at most one coloured region per screen.** Given the above,
  expect almost none. If a screen has two, say why.
- **Badges only where they carry a state the row cannot say in words.** Pending, blocked, deferred,
  yes. Won, paid, active, no. Three or four a page, not twelve.
- **Two cards abreast is unconditional.** Cards shrink rather than stacking. A group may hold one
  card, which keeps its heading and takes full width.
- **Detail that does not fit goes sideways into a sheet, not down into an accordion.** One exception:
  capture during a live call, where collapsible sections win with counts on the headers.
- **A capability that will exist advertises. A gap the model cannot answer is left out.** The test is
  whether somebody could make it appear by doing something.
- **Take radius, spacing and type from the design system's component sources**, which carry them
  inline, and say which file each value came from. There is no geometry token layer and there is not
  meant to be one. **Do not invent a scale.**
- **The writing guide bound to the design system is binding, not advisory.** Sentence case, no
  "Submit", and the audience term is **homeowner**.
- **No em dashes**, in a screen or in a reply.

## What to do first

**Then build one screen: the project at beat 19.** Both jobs complete, balance due and uninvoiced.
Hardest state of the most-used container.

**When it is done, give me one line naming anything you invented or reached outside the component set
for.** Not a component record. Just the escape. Records get written later, from the escapes.

## Learned from

- **16 Sep 2026.** The previous round's memo was rejected because groups moved position and changed
  presentation between states with nothing on screen to justify it. **The cause was that each screen
  re-decided its own arrangement**, which happened because nothing fixed the data or the order. This
  handover fixes both, and the order rule is Andrew's own wording.
- **16 Sep 2026.** **One file rather than a reading list**, again. The lesson from 15 September holds:
  a brief that names seven files to go and read will reach five of them at best.
