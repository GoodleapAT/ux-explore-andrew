Boards, stages, sub-statuses, tasks and gates

The configurable project management model, drawn. This is the same content as the written reference beside it, redrawn so the shape is visible without reading the tables. It uses the mid-size worked configuration: three boards, ten stages, five sub-statuses, five gates. Nothing here is new. It exists so the next round can argue with a picture.

A

The five primitives, and why they are five

The central claim of the model is that these are four different things plus a view, and that collapsing any two of them produces a board a contractor cannot read. Most tools collapse sub-status into stage, which is why they end up with thirty columns.

Eligibility is not gating

Eligibility means this does not apply to this job, set by an attribute rule, and the contractor should ignore it permanently. Gating means it applies but is not satisfied yet, set by a value or a task state, and the contractor should work toward it.

They must never look the same. Not applicable and not yet done is the distinction a contractor has to make without reading.

One rule engine, four targets

A single attribute-rule mechanism decides stage eligibility, sub-status activation, which value set a sub-status uses, and which tasks load.

The attributes that drive it in practice: funding path, jurisdiction, HOA membership, job type, material, property type.

B

The lifecycle: three boards, ten stages, five gates

The stages run left to right in one line. The boards are ranges over that line, not containers. The five gates sit on transitions, and each one has a reason a contractor would give out loud, which is the test for whether it should exist.

Four of the five gates are internal to a board. Only the first sits on a board boundary, which is why a gate is defined as sitting on a transition rather than between teams. The boundary between Installing and Closeout carries no gate at all.

Known defect, carried forward. The first three stages, New lead, Working and Sold, all happen before anything is sold, so no job exists yet to occupy them. Under Model C those three describe the project, and only the seven from Ops intake onward describe a job. The reference beside this file was written before Model C and still treats all ten as one job-level pipeline. Resolving this is one of the first things the next round has to do.
C

Sub-statuses: the waits nobody on the crew can hurry

Two apply to every job. Three activate only when an attribute says so. They run in parallel with the stage and with each other, which is exactly why they cannot be columns.

The vocabulary collision is real and unresolved. Model C uses scope for a priced, additive unit of a proposal. The insurance sub-status uses Scope received for the carrier’s damage document. Both are correct in their own world and both appear on the same job. One of them has to be renamed before either ships.
D

Tasks, stage by stage

Tasks are where granularity lives, which is what keeps the stage count at ten instead of thirty. Four states, not two: complete, incomplete, not applicable and skipped. Not applicable is set by a rule; skipped is set by a person, and a pattern of skipping is a signal that the default is wrong.

Where tasks come from

Universal. Loaded on every job. Attribute-driven. Loaded from job type, material, funding path. Insurance work adds Meet adjuster on site to Working, and Document damage for supplement to Ops intake.

Generated. Compiled by DeDe from what the contractor has saved in Organization Context. The permit document checklist for a specific municipality is the case that earns this.

Preset, recommend, customise

Every primitive follows the same three steps. GoodLeap ships a default per trade, DeDe proposes changes from what the contractor describes, and the contractor accepts, edits or builds their own.

The minimal and maximal configurations in the written reference exist to prove the model stretches. Five stages and one gate at one end, twenty-four stages and nine gates at the other.

E

How this meets Model C

The project management model was designed before the project container existed. It still holds, but three things have to be settled about where it attaches.

What stays the same

Stage, sub-status, task and gate are unchanged as concepts, and the rule engine is unchanged. Nothing in Model C contradicts any of it.

What moves up

New lead, Working and Sold describe the project, not a job. A project carries its own status: pursuing, production, closing, closed, archived.

What stays at the job

Ops intake through Closed. Two jobs from one signed proposal each run this independently and will not stay in step.

What is undecided

Whether a gate can span two jobs in one project, and whether a project shows a rolled-up stage at all or only its own status.

  1. If two jobs in a project are at different stages, what does the project row on a board show?
  2. Do sub-statuses attach to the job, the project, or either? Permit is plausibly per job; financing is clearly per project.
  3. Does a change order that crosses the financing headroom create a gate, and if so on which transition?
  4. Which of the two “scopes” gets renamed.
