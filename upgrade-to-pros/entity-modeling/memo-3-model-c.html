The project is the container

A project holds one piece of business end to end: the opportunities that started it, the proposal that priced it, the contract and the money, and the jobs that deliver it. Inside the project nothing is nested. Opportunities, proposals and jobs sit alongside each other and point at one another.

Taken as settled for this memoEight assumptions, agreed here rather than decided elsewhere ▸
  • A project is always mandatory. Every sale and every piece of work sits inside one, including a lone payment request at the payments tier. There is no second path for work without a project.
  • One acceptance, one contract, one financing per bundled sale. Whether that lands on a proposal holding scopes or on a folio holding discrete proposals is an engineering decision, not something a contractor picks.
  • Opportunities, proposals and jobs are peers inside the project. The proposal is not the parent of jobs.
  • Scopes drive jobs. A scope carries its own statement of work, estimate and itemisation, and it is what a job traces back to.
  • An opportunity links into a project rather than moving into it, so one that is declined survives and can be pursued later.
  • The change order is the boundary test. If an addition can ride on the existing contract, financing and master invoice it is a change order. If it cannot, it is a new project.
  • Projects can be linked to one another where timing, coordination or order of operations matters.
  • Projects get their own status vocabulary. Jobs run their own kanban pipeline underneath.
The thing to decide before anything is builtCan a proposal hold scopes? ▸

Section C draws this as a fork, and it is the only question on this page that changes what gets built rather than how it looks.

If the proposal can be extended to hold several scopes, each with its own price and its own job, the change is contained. Today a proposal holds exactly one scope, so the scope becomes a repeatable unit, but acceptance, contract and financing stay where they already live.

If it cannot, the proposal is left as it is and a folio has to be built above it, given one acceptance, one contract signing and one financing. That is a second object carrying contract semantics, not a presentation wrapper, and it is a materially larger piece of work.

Everything after signing is identical either way, so the screens can be designed while this is still open. It does not block design; it blocks build.

Worth noting separately: "project" is already taken in Merlin as a design artefact carrying a bill of materials and an electricity profile.

The only containment here is the project. Everything inside it is a peer, and every arrow is an association rather than ownership. Roofing was quoted and not bought, so it stays on the customer with its link intact.

The container is not a document

A project exists before anything is priced and is never sent to anyone. Earlier models tried to make the customer-facing artefact do this job, which is why financing, the master invoice and the change order kept landing in awkward places. Separating the workspace from the artefact puts each of them somewhere obvious.

Opportunities belong to the customer

They exist before any project does, they carry their provenance from the moment they are created, and they survive the project ending. Drawing them outside the frame is the honest picture: a project borrows them.

Depth stops at two

Customer, then project, then a flat set of peers. It looks deeper than it is because there are several kinds of thing inside, but nothing is nested under anything except the project, so there is no hierarchy to navigate.

B

The same project, including the sale

Three opportunities, one proposal that changes twice, two jobs

Amounts are illustrative. Roofing is drawn as an ordinary opportunity with its provenance, because the decline is told by the proposal moving from state one to state two rather than by labelling the opportunity.

The toggle is the partial-acceptance mechanism

Earlier models had no way to vary an offer before signing, which is why declining half a proposal was so awkward. Toggling handles variation before the signature and change orders handle it after. That split is clean and neither earlier model had it.

A suggested scope is priced but off

Windows was never a customer interest. It is on the proposal, costed, and switched off, so raising it in the room costs one tap rather than a rebuild. That is the contractor-identified opportunity earning its place in the flow rather than sitting in a list.

The money arrives late and then holds still

Nothing on the right exists until the proposal is signed, and once it does it belongs to the project rather than to whatever created it. That is what makes the balance answerable at one level instead of three.

C

Two ways to build the bundled sale, only one gets built

An engineering fork, not a contractor-facing choice

This is a build decision, not a feature

A contractor never picks between these. One of them ships and the other does not. The reason it is drawn at all is that the choice changes what has to be invented, and the memo should not assume the easier answer is available.

Both branches are work, and not the same work

Today's proposal holds a single scope, so neither branch is free. The preferred one extends an object that already exists. The fallback leaves it alone and creates one that does not, then has to give it acceptance, signing and financing. The question is where the contract semantics end up, not whether to build.

Downstream is identical either way

One acceptance, one contract, one financing, and one job per priced unit. Whether that unit is called a scope inside a proposal or a proposal inside a folio, everything after signing behaves the same. That is what makes this safe to defer.

D

Where one project ends and another begins

The boundary test

A test, not a judgement

"Where does a project end" is the kind of question that gets answered differently by every contractor and then argued about forever. Anchoring it to whether the money can ride along turns it into something the system can recommend rather than the user having to feel.

The contractor still chooses

The test produces a recommendation, sometimes a strong one, not a rule. Someone who wants one project per address, or one per year, should be able to work that way and live with the consequences.

Links are a fourth relationship

The model now has customer to project, project to its contents, associations between those contents, and links between projects. Worth writing down, because the fourth one arrived last and is the easiest to lose.
